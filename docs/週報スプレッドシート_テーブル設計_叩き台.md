# 週報スプレッドシート テーブル設計（叩き台）

## 0. この設計で実現したいこと（要件整理）

現状：週報が「Excelファイル単位（今週=ファイルA / 来週=ファイルB）× 人数分」で分散管理。

移行後にやりたいこと：

1. **1案件を1行**で、取り組み内容・コメント/課題・進捗率・予定（いつやるか）を記録したい
2. スプレッドシートの**キャンバス機能**からタスクを登録したい
3. 登録したタスクが**ダッシュボード**としてキャンバスに表示される
4. **作業時間**を記録し、日／週で**大分類ごとの円グラフ**を出したい
5. 円グラフの大分類（例：電話対応）で**絞り込み（ドリルダウン）**して、
   「どの案件／どのタスクに時間を取られたか」まで掘り下げたい

---

## 1. 設計方針：「1案件1行」と「時間記録」は別テーブルに分ける

ここが今回の設計で一番大事なポイントです。

- ユーザーが望む **「1案件1行」** は、案件の“今の状態”を俯瞰する **マスタ的なビュー** としては正しい。
- しかし **作業時間** は「同じ案件を月・火・水…と複数日にわたって作業する」ため、
  1案件に対して **時間の記録は複数行** 発生します。
- したがって **1案件1行の中に時間を持たせると、円グラフ・ドリルダウンが作れません**。

→ そこで **「案件（マスタ）」と「作業ログ（明細）」を分離** します。
   - 案件マスタ ＝ 1案件1行（俯瞰・進捗管理用）
   - 作業ログ ＝ 1作業1行（時間集計・ドリルダウン用）

この2つを **案件ID** で繋ぐことで、両方の見せ方（1案件1行の一覧 と 時間の円グラフ）が両立します。

---

## 2. テーブル一覧（4テーブル構成）

| # | テーブル名 | 役割 | 粒度（1行の意味） |
|---|-----------|------|------------------|
| 1 | `M_案件` | 案件マスタ | 1案件 = 1行 |
| 2 | `T_作業ログ` | 作業実績（時間） | 1作業（案件×日×作業内容）= 1行 |
| 3 | `T_予定` | 来週の予定・タスク | 1予定タスク = 1行 |
| 4 | `M_大分類` | 分類マスタ | 1分類 = 1行 |

### テーブル間の関係（ER）

```
        M_大分類 (大分類ID)
             ▲
             │ 参照
     ┌───────┴────────┐
   M_案件           T_作業ログ
 (案件ID) ◄───────── (案件ID, 大分類ID)
     ▲
     │ 参照
   T_予定 (案件ID)
```

- **案件ID** … 全テーブルをつなぐ主キー／外部キー（結合の軸）
- **大分類ID** … 円グラフの分類軸（表記ゆれ防止のためマスタ化）

> ※ `T_予定` と `T_作業ログ` は「区分（予定／実績）」列を持つ**1テーブルに統合**する案もあります（後述 8-A）。まずは分けた形で提示します。

## 3. テーブル定義

### 3-1. `M_案件`（案件マスタ）＝ 1案件1行

案件の“今の状態”を俯瞰する、ユーザーが望む「1案件1行」のビュー。

| 列名 | 型 | 例 | 説明 |
|------|----|----|------|
| 案件ID | ID(PK) | C-0001 | 一意キー。全結合の軸 |
| 案件名 | 文字 | ○○社 見積作成 | |
| 大分類ID | 参照 | K01 | `M_大分類`を参照（主となる分類） |
| 担当者 | 文字 | 山田 | |
| ステータス | 選択 | 進行中 | 未着手／進行中／完了／保留 |
| 進捗率 | 数値% | 60 | 案件全体の進捗（手入力 or 自動※後述） |
| 取り組み内容（概要） | 文字 | 要件ヒアリング〜見積 | 案件レベルの説明 |
| コメント／課題 | 文字 | 先方回答待ち | 案件レベルの課題 |
| 開始日 | 日付 | 2026-06-23 | |
| 期限 | 日付 | 2026-07-10 | |
| 完了日 | 日付 | | 完了時に記録 |
| 累計作業時間 | 数値h | 12.5 | `T_作業ログ`から自動集計（SUMIF等） |

> **進捗率・累計作業時間の自動化**：`T_作業ログ`から `SUMIF(案件ID)` で累計時間を、
> 予定/完了タスク数から進捗率を自動計算する運用も可能。まずは手入力でも可。

---

### 3-2. `T_作業ログ`（作業実績）＝ 1作業1行  ★時間集計・円グラフの心臓部

**「その日やったこと」＋「かかった時間」** を1行ずつ記録。ここが円グラフ／ドリルダウンの元データ。

| 列名 | 型 | 例 | 説明 |
|------|----|----|------|
| ログID | ID(PK) | L-00001 | |
| 案件ID | 参照 | C-0001 | `M_案件`を参照（ドリルダウンの軸） |
| 作業日 | 日付 | 2026-06-30 | 日／週の集計軸 |
| 担当者 | 文字 | 山田 | |
| 大分類ID | 参照 | K02 | `M_大分類`参照。円グラフの軸 ※注 |
| 作業内容（実績） | 文字 | 電話で仕様確認 | その日やったこと |
| 作業時間(h) | 数値 | 1.5 | 円グラフの値 |
| コメント／課題 | 文字 | 追加依頼あり | その作業の気づき |
| 進捗率(時点) | 数値% | 40 | （任意）その時点の進捗スナップショット |

> **※大分類IDを作業ログ側にも持つ理由**：
> 同じ案件でも日によって作業の性質が変わる（例：ある案件で「電話対応」もすれば「資料作成」もする）。
> 「電話対応にどれだけ時間を使ったか」を正確に出すには、**時間の行ごとに大分類が必要**です。
> 案件レベルの大分類（`M_案件`側）と役割が違う点に注意。
> （運用を軽くしたいなら、作業ログの大分類は空欄時に案件の大分類を継承、でもOK）

---

### 3-3. `T_予定`（来週の予定・タスク）＝ 1タスク1行

キャンバスから登録する「これからやること」。来週の予定＝未来のタスク。

| 列名 | 型 | 例 | 説明 |
|------|----|----|------|
| 予定ID | ID(PK) | P-00001 | |
| 案件ID | 参照 | C-0001 | `M_案件`を参照 |
| 予定日／週 | 日付 | 2026-07-07 | いつやるか |
| 予定作業内容 | 文字 | 見積書送付 | |
| 担当者 | 文字 | 山田 | |
| 見積時間(h) | 数値 | 2 | （任意）予実比較に使える |
| ステータス | 選択 | 未着手 | 未着手／進行中／完了 |

> 完了したら `T_作業ログ` に実績（実時間）を1行足す運用。
> これで「予定（見積）」と「実績（実時間）」の**予実比較**もできる。

---

### 3-4. `M_大分類`（分類マスタ）＝ 円グラフの分類軸を固定

**円グラフがブレない**ために必須。手入力の表記ゆれ（"電話"／"電話対応"／"TEL"）を防ぐ。

| 列名 | 型 | 例 | 説明 |
|------|----|----|------|
| 大分類ID | ID(PK) | K02 | |
| 大分類名 | 文字 | 電話対応 | 円グラフの凡例に出る名前 |
| 表示順 | 数値 | 2 | グラフの並び順 |
| 色 | 文字 | #4285F4 | （任意）円グラフの色固定 |

> `M_案件` と `T_作業ログ` の大分類列は、この表を**プルダウン（データの入力規則）**にする。
> 中分類・小分類まで管理したい場合は列を足す or `M_中分類` を追加（8-B参照）。

---

## 4. Q：「この構成で、全テーブルが繋がったダッシュボードは作れる？」→ **はい、作れます**

条件は2つだけです。

1. **共通キー = 案件ID** を全テーブルに必ず持たせる（結合の軸）
2. **大分類はマスタ参照（プルダウン）** にして表記を統一する（集計軸）

この2つが守られていれば、以下のように**1つのダッシュボードから全部が繋がります**：

- 案件一覧（`M_案件`）で案件を選ぶ
  → その案件の作業明細（`T_作業ログ`）と予定（`T_予定`）が芋づる式に出る
- 大分類の円グラフ（`T_作業ログ`を大分類で集計）で分類を選ぶ
  → その大分類に該当する作業ログ→案件が絞り込まれる

逆に、この2つが崩れると繋がりません：
- 案件IDが無い／表記が案件名頼み → 結合できず一覧と時間が連動しない
- 大分類がフリー入力 → 「電話対応」と「電話」が別分類扱いになり円グラフが割れる

---

## 5. Q：作業時間の円グラフ＆ドリルダウンは？→ この設計で実現できます

### 集計の元データ
すべて `T_作業ログ`（1作業1行、案件ID・作業日・大分類ID・作業時間を持つ）から作ります。

### ① 大分類別の円グラフ（日／週）
```
値   = SUM(作業時間)
分類 = 大分類名（M_大分類）
絞り = 作業日 = 対象の日 / 対象の週
```
→ ピボット or `SUMIFS(作業時間, 大分類, 各分類, 作業日, 期間)` で作成。

### ② ドリルダウン（大分類 → 案件 → タスク）
```
[Lv1] 大分類で絞る（例：電話対応）
  ↓  T_作業ログ を 大分類ID = "電話対応" でフィルタ
[Lv2] 案件ごとに時間を集計（どの案件に取られたか）
  ↓  GROUP BY 案件ID → SUM(作業時間) を棒グラフ/表で
[Lv3] 個別の作業明細（いつ・何を・何時間）
      T_作業ログ の該当行をそのまま表示
```

これが成立するのは、**時間データが「案件ID＋大分類ID＋作業時間」を1行ずつ持っている**からです。
（＝ 1案件1行に時間を畳み込んでいたら、この掘り下げは不可能）

## 6. 週報としての“見せ方”（既存運用のマッピング）

| 既存の週報の要素 | 新設計での出どころ |
|-----------------|-------------------|
| 取り組んだ内容 | `M_案件`.取り組み内容 ＋ `T_作業ログ`.作業内容 |
| その日やったこと | `T_作業ログ`（作業日で絞る） |
| 課題・コメント | `M_案件`.コメント／`T_作業ログ`.コメント |
| 進捗率 | `M_案件`.進捗率 |
| 未完了タスク一覧 | `T_予定`／`M_案件` の ステータス≠完了 で抽出 |
| 来週の予定 | `T_予定`（予定日が来週の行） |
| 作業時間・円グラフ | `T_作業ログ`.作業時間 を大分類で集計 |

→ 週報は「テーブルから条件で切り出したビュー」になり、**Excelを人数分×週数分作る運用が不要**に。

---

## 7. キャンバス登録フローとの関係（概要）

キャンバスからの登録は、基本的に **`T_予定` か `T_作業ログ` への1行追加** に対応させます。

- 「これからやること」を登録 → `T_予定` に追加
- 「やったこと＋時間」を登録 → `T_作業ログ` に追加
- 新しい案件なら先に `M_案件` に1行

> 登録用キャンバスのプロンプト設計は次ステップ。
> ポイントは「入力時に**案件IDと大分類をプルダウンで選ばせる**」＝ 手入力させないこと。
> これがダッシュボード連結・円グラフ精度の生命線になります。

## 8. 検討オプション（叩き台への論点）

**8-A. 予定と実績を1テーブルに統合するか**
`T_予定`と`T_作業ログ`を `T_タスク`（列に「区分：予定/実績」）で1本化する案。
- 長所：入力先が1つで分かりやすい、予実が同じ行で見やすい
- 短所：予定と実績で必要な列が少し違う（見積時間 vs 実時間）ため列がやや冗長

**8-B. 中分類・小分類をどこまで持つか**
「電話対応」の下に「新規／既存／クレーム」等を持つなら、`M_中分類`を追加 or 大分類マスタに階層列。

**8-C. 進捗率を自動にするか手入力にするか**
自動化するなら「完了タスク数 ÷ 全タスク数」等の定義を決める必要あり。まずは手入力を推奨。

**8-D. 担当者マスタを持つか**
部署の人数分で回すなら `M_担当者` を足すと、人別の集計（誰が何に時間を使ったか）も同じ仕組みで可能。
